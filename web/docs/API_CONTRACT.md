# 웹·모바일 공통 API 규격 제안

상태: **팀 합의 전 제안**. 실제 서버 스펙 또는 Jira 본문에서 확정된 규격이 아닙니다.
`src/shared/api/contracts.ts`는 DOM·React 의존성이 없는 타입 제안이며 모바일 코드를 수정하거나 공유 패키지를 배포하지 않았습니다.

## 응답

성공 응답은 HTTP 2xx와 `{ "data": ... }`, 본문 없는 성공은 HTTP 204를 제안합니다.
실패는 적절한 HTTP 4xx/5xx와 다음 형태를 제안합니다.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "입력값을 확인해 주세요.",
    "fieldErrors": { "name": ["이름을 입력해 주세요."] }
  }
}
```

`code`는 프로그램 분기용 고정 값, `message`는 사용자 표시 후보이며 UI에서 안전한 기본 문구를 제공해야 합니다.
서버 내부 예외·스택·비밀정보는 응답에 포함하지 않습니다.
HTTP 상태가 실패 여부의 기준이며 200 응답에 실패 플래그를 넣지 않는 방향을 제안합니다.

## 목록 및 데이터

페이지 응답 `data`는 `{ items, page, size, totalElements, totalPages }` 형태로 제안합니다.
페이지 번호는 0부터 시작합니다. 커서 페이지네이션이 필요한 경우 별도 규격을 합의합니다.
식별자는 문자열, 일시는 시간대가 포함된 ISO 8601 문자열, JSON 필드는 camelCase를 제안합니다.
필드 누락과 null의 의미는 엔드포인트 스키마에 명시합니다.

## 확정이 필요한 항목

- 백엔드 기본 URL·버전 경로·OpenAPI 문서
- 인증 방식, 만료·갱신 흐름, 쿠키/CORS/CSRF 정책
- 실제 성공·오류 envelope와 오류 코드 목록
- 페이지 번호·정렬·검색 규칙 및 날짜/ID 표현
- 파일 업로드 규칙과 제한
- 모바일과 타입을 공유할 패키지 또는 OpenAPI 생성 방식

현재 클라이언트는 이 제안을 강제하거나 자동 unwrap하지 않습니다. 실제 응답에 맞춰 호출 타입을 정의하고
합의 후 계약 타입과 테스트를 함께 갱신합니다. 실제 서버와의 통합 검증 전에는 API 관련 이슈를 완료로 간주하지 않습니다.
