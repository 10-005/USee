# Git·Jira 협업 규칙

> 프로젝트: **S15P31D106**  
> 적용 파트: **Mobile / Web / Backend / AI**  
> 적용 범위: Commit, Branch, Merge Request, Jira Issue, Sprint

본 문서는 팀의 작업 단위를 Jira로 관리하고, Git 변경 이력과 연결하기 위한 공통 협업 규칙을 정의한다.

## 1. 공통 원칙

1. 개발·수정·문서·인프라 작업은 원칙적으로 Jira 이슈를 기준으로 진행한다.
2. 작업 브랜치, Commit, Merge Request(MR)에 **동일한 Jira 이슈 번호**를 기재한다.
3. 직접 Push를 금지한 통합 브랜치에는 MR을 통해서만 변경 사항을 반영한다.
4. 작업 브랜치의 기본 병합 대상은 해당 파트의 `develop-*` 브랜치이다.
5. 이슈의 `Done` 여부는 **코드 작성 완료가 아니라 검증 및 병합 완료**를 기준으로 판단한다.

예시에서 사용하는 `S15P31D106-91` 등의 번호는 형식 설명을 위한 **가상 Jira 이슈 번호**이다. 실제 작업에서는 Jira가 발급한 번호를 사용한다.

## 2. Commit Convention

### 2.1. 커밋 메시지 형식

```text
태그: 제목

본문 (선택)

S15P31D106-이슈번호
```

- **제목**: 변경 사항을 간결하게 요약한다.
- **본문**: 무엇을 변경했고 왜 변경했는지 설명한다. 필요한 경우에만 작성한다.
- **마지막 줄**: 관련 Jira 이슈 번호를 반드시 작성한다.
- 제목·본문·이슈 번호 사이에는 빈 줄을 둔다. 본문이 없는 경우 제목과 이슈 번호 사이에 빈 줄을 둔다.

### 2.2. 작성 규칙

#### 제목

- `태그: 제목` 형식을 사용하고, 태그는 영문 소문자로 작성한다.
- 제목은 한글을 기본으로 하며, `구현`, `수정`, `추가`, `분리`처럼 변경 내용을 명확히 나타낸다.
- 태그를 포함하여 **50자 이내**로 작성한다.
- 끝에 마침표를 붙이지 않는다.

#### 본문

- 제목만으로 충분히 설명되지 않는 경우 작성한다.
- 여러 변경 사항은 하이픈(`-`)으로 나누어 적는다.
- 구현 세부 사항을 나열하는 데 그치지 않고, 변경 내용과 이유가 드러나도록 작성한다.

#### Jira 이슈 번호

- 마지막 줄에 `S15P31D106-번호` 형식으로 작성한다.
- `Jira:`, `Refs:`, `Closes:` 등의 접두어는 사용하지 않는다.
- 여러 커밋이 하나의 이슈에 연결될 수 있지만, **각 커밋에도 이슈 번호를 표기**한다.

### 2.3. Commit Tag

| 태그 | 사용 목적 | 예시 |
|---|---|---|
| `init` | 프로젝트 초기 설정 | 초기 프로젝트 구조 구성 |
| `feat` | 새로운 기능 추가 | 실종 신고 목록 조회 기능 구현 |
| `fix` | 버그 수정 | 이미지 미리보기 갱신 오류 수정 |
| `refactor` | 동작 변경 없는 코드 구조 개선 | 화면 상태 관리 로직 분리 |
| `design` | UI·디자인 변경 | 보호동물 카드 UI 수정 |
| `docs` | 문서 변경 | API 명세서 갱신 |
| `test` | 테스트 코드 추가·수정 | 실종 신고 조회 테스트 추가 |
| `build` | 빌드·의존성 설정 변경 | 라이브러리 버전 변경 |
| `ci` | CI/CD 설정 변경 | 빌드 파이프라인 구성 |
| `chore` | 위 분류에 속하지 않는 유지보수 | 개발 환경 설정 정리 |

> **구분:** 브랜치의 새 기능 타입은 `feature/`이고, 해당 기능의 Commit Tag는 `feat:`이다.

### 2.4. 작성 예시

#### 기능 개발

```text
feat: 실종 신고 목록 조회 기능 구현

- 실종 신고 목록 API 연동
- 조회 결과를 화면 상태에 반영

S15P31D106-91
```

#### 디자인 수정

```text
design: 보호동물 상세 화면 UI 수정

- 입양 신청 버튼 위치 조정
- 동물 정보 영역 간격 수정

S15P31D106-92
```

#### 버그 수정

```text
fix: 이미지 업로드 후 미리보기 오류 수정

이미지 변경 직후 이전 미리보기가 남는 문제 해결

S15P31D106-93
```

#### 리팩토링

```text
refactor: 실종 신고 화면 상태 변환 로직 분리

화면 상태 변환 책임을 별도 구성 요소로 이동

S15P31D106-94
```

#### 간단한 변경 (본문 생략)

```text
docs: README 실행 방법 수정

S15P31D106-95
```

## 3. Branch Strategy

### 3.1. 브랜치 구조

```text
master
└── develop
    ├── develop-mobile
    │   ├── feature/S15P31D106-91-missing-report-list
    │   └── fix/S15P31D106-93-image-preview
    │
    ├── develop-web
    │   └── feature/S15P31D106-101-shelter-dashboard
    │
    ├── develop-backend
    │   └── feature/S15P31D106-111-missing-report-api
    │
    └── develop-ai
        └── feature/S15P31D106-121-animal-embedding
```

위 그림은 **브랜치 생성·병합 관계를 표현한 개념도**이며, Git에 실제 부모·자식 브랜치 계층이 존재한다는 의미는 아니다.

### 3.2. 브랜치 역할

| 브랜치 | 역할 | 변경 사항 유입 경로 |
|---|---|---|
| `master` | 배포·발표 가능한 안정 버전 관리 | `develop`에서 MR |
| `develop` | Mobile·Web·Backend·AI 전체 통합 및 연동 테스트 | 각 `develop-*`에서 MR |
| `develop-mobile` | Mobile 파트 코드 통합 | Mobile 작업 브랜치에서 MR |
| `develop-web` | Web 파트 코드 통합 | Web 작업 브랜치에서 MR |
| `develop-backend` | Backend 파트 코드 통합 | Backend 작업 브랜치에서 MR |
| `develop-ai` | AI 파트 코드 통합 | AI 작업 브랜치에서 MR |

- `master`, `develop`, 모든 `develop-*` 브랜치에는 **직접 Push하지 않는다**.
- 작업 브랜치는 자신의 파트별 `develop-*` 브랜치에서 생성한다.
- 공통 설정이나 인프라처럼 특정 파트에 속하지 않는 작업은 **시작 전에 담당 파트와 병합 대상을 결정**한다.

### 3.3. 작업 브랜치 네이밍

```text
타입/Jira이슈번호-작업내용
```

예시:

```text
feature/S15P31D106-91-missing-report-list
fix/S15P31D106-93-image-preview
refactor/S15P31D106-94-missing-state
design/S15P31D106-102-shelter-ui
```

- Jira 이슈 번호를 반드시 포함한다.
- 작업 내용에는 **영문 소문자, 숫자, 하이픈(`-`)**을 사용한다.
- 단어 사이는 하이픈으로 구분하고, 작업 내용을 짧고 구체적으로 작성한다.
- 원칙적으로 **하나의 Jira 작업 이슈에 하나의 작업 브랜치**를 대응시킨다.

#### Branch Type

| 접두어 | 용도 |
|---|---|
| `feature` | 신규 기능 개발 |
| `fix` | 버그 수정 |
| `refactor` | 리팩토링 |
| `design` | UI·디자인 변경 |
| `docs` | 문서 변경 |
| `test` | 테스트 작업 |
| `build` | 빌드·의존성 설정 |
| `ci` | CI/CD 설정 |
| `chore` | 기타 유지보수 |

### 3.4. 개발 및 통합 흐름

```text
작업 브랜치
    │  MR (작업 검증·코드 리뷰)
    ▼
해당 파트 develop-*
    │  MR (파트 단위 통합)
    ▼
develop
    │  MR (전체 기능·통합 테스트 완료 후)
    ▼
master
```

전체 통합 방향:

```text
develop-mobile  ──┐
develop-web     ──┤
develop-backend ──┼──→ develop ──→ master
develop-ai      ──┘
```

예시:

```text
feature/S15P31D106-91-missing-report-list
                    ↓ MR
              develop-mobile
                    ↓ MR
                 develop
                    ↓ MR
                  master
```

### 3.5. Merge 규칙

- 모든 변경은 Merge Request를 통해 병합한다.
- MR에는 **최소 1명 이상의 리뷰**가 필요하다.
- 병합 전 충돌을 해결하고, 변경 범위에 맞는 빌드·테스트·기본 동작을 확인한다.
- 작업 브랜치는 가능한 짧게 유지하고, Merge 완료 후 삭제한다.
- `develop`으로 병합하는 시점에는 파트 간 연동 및 영향 범위를 확인한다.
- `master`에는 전체 기능 및 통합 테스트를 통과한 안정 버전만 병합한다.

### 3.6. Merge 방식

| 병합 방향 | 권장 방식 | 이유 |
|---|---|---|
| 작업 브랜치 → `develop-*` | **Squash Merge 권장** | Jira 작업 단위로 Commit History 정리 |
| `develop-*` → `develop` | **Squash하지 않고 병합** | 파트별 작업 이력 유지 |
| `develop` → `master` | **Squash하지 않고 병합** | 전체 개발·통합 이력 유지 |

작업 브랜치에서 여러 커밋을 작성한 경우:

```text
feat: 실종 신고 카드 UI 구현
feat: 실종 신고 목록 API 연동
fix: 로딩 상태 처리 수정
```

Squash Merge 후 커밋 메시지:

```text
feat: 실종 신고 목록 조회 기능 구현

- 목록 UI와 API 연동
- 로딩 및 오류 상태 처리

S15P31D106-91
```

> Squash Merge를 사용해도 최종 커밋 메시지는 **Commit Convention**을 따른다.

## 4. Jira 이슈 운영 규칙

### 4.1. Jira 사용 목적

- 기능·버그·리팩토링·디자인·테스트·인프라·문서 작업을 이슈 단위로 관리한다.
- 담당자, 진행 상태, 완료 조건, 관련 작업을 추적한다.
- Git의 Branch·Commit·MR과 Jira 이슈 번호를 연결한다.
- Sprint별 목표와 작업 범위를 계획하고 완료 여부를 점검한다.

### 4.2. Issue Hierarchy 및 연결 방식

Jira 기본 계층 구조를 기준으로 다음과 같이 운영한다.

```text
Epic (기능 영역)
├── Story (사용자 기능)
│   ├── Sub-task: [Mobile] 구현 작업
│   ├── Sub-task: [Backend] 구현 작업
│   └── Sub-task: [AI] 구현 작업
├── Task (독립 작업)
└── Bug (독립 오류)
```

- **Epic**: 서비스의 큰 기능 영역을 나타낸다.
- **Story**: 사용자에게 제공하는 하나의 기능을 정의한다.
- **Sub-task**: Story를 실제 구현할 파트별 세부 작업으로 나눈다.
- **Task**: 특정 Story의 하위 작업이 아닌 독립적인 개발·인프라·문서 작업을 관리한다.
- **Bug**: 발견된 결함을 관리하고, 관련 Story 또는 Task와 연결한다.

> Jira 기본 설정에서는 **Story·Task·Bug가 같은 계층**이다. 따라서 Story 아래의 세부 구현 작업은 `Sub-task`를 사용한다. 팀 Jira에서 별도 계층을 설정한 경우에는 해당 설정을 따른다. 이 문서에서 '작업 이슈'는 Task와 Sub-task를 함께 지칭한다.

#### Epic

기능·도메인 중심으로 작성한다.

```text
회원 및 인증
반려동물 관리
실종 신고
발견 신고
구조 관리
보호동물 관리
입양 관리
AI 이미지 매칭
알림 및 채팅
보호소 관리
```

- 파트 이름이나 특정 기술을 Epic으로 사용하지 않는다.
- 하나의 Epic은 여러 Story와 Sprint를 포함할 수 있다.

#### Story

제목은 사용 주체와 행동이 드러나는 **`[주체]가 [행동]한다`** 형식으로 작성한다.

```text
일반회원이 카카오 계정으로 로그인한다
일반회원이 실종 신고 목록을 조회한다
일반회원이 반려동물을 등록한다
보호소 담당자가 입양 신청서를 심사한다
```

- 사용자에게 제공할 기능을 기준으로 나눈다.
- 구현 기술이나 개발 파트는 제목에 넣지 않는다.
- 기능 설명과 완료 조건을 작성한다.

#### Sub-task / Task

제목은 **`[파트] 구체적인 작업 내용`** 형식으로 작성한다.

```text
[Mobile] 실종 신고 목록 화면 구현
[Web] 보호소 관리 대시보드 구현
[Backend] 실종 신고 목록 조회 API 구현
[AI] 동물 이미지 임베딩 생성 기능 구현
[Infra] 이미지 저장 환경 구성
[Common] API 명세서 작성
```

- `[Mobile]`, `[Web]`, `[Backend]`, `[AI]`, `[Infra]`, `[Common]`을 사용한다.
- 가급적 **한 명이 하나의 브랜치로 완료할 수 있는 범위**로 나눈다.
- 여러 담당자 또는 독립적인 검증이 필요한 작업은 분리한다.
- 해당 작업을 검증할 수 있는 완료 조건을 작성한다.

#### Bug

제목은 **`[파트] 문제 내용 수정`** 형식으로 작성한다.

```text
[Mobile] 이미지 업로드 후 미리보기 갱신 오류 수정
[Web] 보호소 목록 필터 초기화 오류 수정
[Backend] 토큰 만료 처리 오류 수정
[AI] 일부 이미지의 유사도 계산 실패 오류 수정
```

- 문제 현상, 재현 방법, 기대 결과, 실제 결과를 작성한다.
- 관련 Story·Task와 이슈 링크로 연결한다.
- 독립적인 수정이 필요하면 별도 Bug로 관리한다.

### 4.3. Issue Description 템플릿

#### Story

```markdown
## 기능 설명
- 사용자에게 제공할 기능을 작성한다.

## 완료 조건
- 사용자 기능의 정상 동작을 판단할 기준을 작성한다.

## 참고
- 관련 정책, Figma, API 명세, 참고 이슈
```

#### Task / Sub-task

```markdown
## 작업 내용
- 구현하거나 변경할 내용을 작성한다.

## 완료 조건
- 검증 가능한 완료 기준을 작성한다.

## 참고
- 관련 Story, Figma, API 명세, 문서 등
```

예시: `[Mobile] 실종 신고 목록 화면 구현`

```markdown
## 작업 내용
- 실종 신고 목록 UI 구현
- 목록 조회 API 연동
- 로딩 및 오류 상태 처리

## 완료 조건
- 목록 데이터가 정상적으로 표시된다.
- 로딩 및 오류 상태가 구분되어 표시된다.
- 목록 선택 시 상세 화면으로 이동한다.

## 참고
- 실종 신고 목록 화면 설계
- 관련 API 명세
```

#### Bug

```markdown
## 문제 현상
- 오류의 발생 상황을 작성한다.

## 재현 방법
1. 오류를 재현하는 순서를 작성한다.
```

### 4.4. Issue Status

```text
To Do → In Progress → In Review → Done
```

| 상태 | 전환 기준 |
|---|---|
| `To Do` | 작업을 시작하지 않음. 담당자가 정해져도 작업 전이면 유지 |
| `In Progress` | 작업 브랜치를 생성하고 실제 작업을 시작함 |
| `In Review` | MR을 생성하고 코드 리뷰·기능 검증을 진행함 |
| `Done` | 완료 조건을 충족하고 대상 브랜치에 병합함 |

- 리뷰에서 추가 수정이 필요하면 기존 작업 브랜치에 반영한다. 필요시 상태를 `In Progress`로 되돌린다.
- **작업 이슈의 Done**과 **Story의 Done**을 구분한다. Story는 관련 개발 작업뿐 아니라 기능 연동 및 Story 완료 조건까지 검증한 후 완료한다.
- Epic은 관련 기능들이 완료되고 해당 기능 영역의 목표를 충족하면 완료한다.
- 코드 변경이나 MR이 필요하지 않은 문서·조사 등은 해당 작업의 완료 조건에 따라 `Done`으로 처리한다.

### 4.5. Jira와 Git의 연결

하나의 작업 이슈를 다음과 같이 연결한다.

```text
Jira:   S15P31D106-91  [Mobile] 실종 신고 목록 화면 구현
  ↓
Branch: feature/S15P31D106-91-missing-report-list
  ↓
Commit: feat: 실종 신고 목록 조회 기능 구현
        ...
        S15P31D106-91
  ↓
MR:     S15P31D106-91 실종 신고 목록 조회 기능 구현
  ↓
Merge:  develop-mobile
```

- 하나의 작업 이슈에서 **여러 Commit**을 작성할 수 있다.
- 독립적으로 개발·리뷰할 작업은 별도 이슈와 작업 브랜치로 분리한다.
- MR 제목에도 Jira 이슈 번호를 포함한다.
- Jira 화면에서 Git 이력을 직접 확인하려면 저장소와 Jira 간 연동 설정이 필요하다.

### 4.6. 담당 파트 관리

| 파트 | 이슈 제목 접두어 | 권장 Component |
|---|---|---|
| Mobile | `[Mobile]` | `Mobile` |
| Web | `[Web]` | `Web` |
| Backend | `[Backend]` | `Backend` |
| AI | `[AI]` | `AI` |
| 인프라 | `[Infra]` | `Infra` |
| 공통 작업 | `[Common]` | `Common` |

- **Epic은 기능 영역**, **Story는 사용자 기능**, **작업 이슈는 구현 단위**, **Component는 담당 파트**를 나타낸다.
- 한 기능에 여러 파트가 참여하더라도 동일 기능의 Story를 파트별로 중복 생성하지 않는다.
- `Component`는 Jira 프로젝트 설정과 권한에 따라 이용 가능 여부를 확인한다. 사용하기 어렵다면 제목 접두어로 구분한다.

### 4.7. Sprint 운영

Sprint 계획과 이슈 상태는 구분한다. **Backlog / Sprint는 작업 배치**, **To Do ~ Done은 진행 상태**이다.

#### Sprint 시작 전

1. Sprint 목표와 구현할 Story를 선정한다.
2. 필요한 Task·Sub-task를 나누고 담당자를 지정한다.
3. 우선순위, 작업량, 의존 관계를 확인한다.

#### Sprint 진행 중

1. 개발 시작 시 상태를 `In Progress`로 변경한다.
2. MR 생성 후 `In Review`, 병합 및 검증 완료 후 `Done`으로 변경한다.
3. 새 작업은 별도 이슈로 등록하고 현재 Sprint에 포함할지 팀에서 결정한다.
4. 진행을 막는 문제가 있으면 해당 이슈에 기록하고 공유한다.

#### Sprint 종료 시

1. `Done` 이슈와 실제 완료 결과가 일치하는지 확인한다.
2. 미완료 이슈를 Backlog 또는 다음 Sprint로 이관한다.
3. 더 이상 필요하지 않은 이슈는 사유를 남기고 정리한다.
4. Sprint 목표 달성 여부 및 미완료 원인을 확인한다.

### 4.8. 작업 크기 기준

적절한 예:

```text
[Mobile] 실종 신고 목록 화면 구현
[Mobile] 실종 신고 목록 API 연동
[Mobile] 실종 신고 상세 화면 구현
```

지나치게 큰 예:

```text
[Mobile] 실종 신고 기능 전체 구현
```

- 서로 다른 기능이거나, 담당자가 다르거나, 독립적으로 검증할 수 있으면 작업을 분리한다.
- 사소한 변경까지 무조건 분리하지는 않는다.
- **하나의 작업 이슈는 명확한 완료 기준을 갖고 한 사람이 한 브랜치에서 완료할 수 있는 크기**를 권장한다.

### 4.9. Definition of Done (DoD)

#### Task / Sub-task / Bug

- [ ] 요구사항 구현 또는 오류 수정 완료
- [ ] 이슈 완료 조건 충족
- [ ] 관련 빌드·테스트 및 핵심 동작 확인
- [ ] MR 코드 리뷰 완료 (코드 변경이 있는 경우)
- [ ] 대상 브랜치에 병합 완료 (코드 변경이 있는 경우)
- [ ] 필요한 문서 및 API 명세 반영

#### Story

- [ ] 관련 작업 이슈 완료
- [ ] 해당 기능에 필요한 파트 간 연동 확인
- [ ] 사용자 기능 정상 동작 확인
- [ ] Story 완료 조건 충족

**작업 이슈가 모두 Done이어도 통합 검증을 완료하지 못했다면 Story는 Done으로 변경하지 않는다.**

## 5. 전체 협업 흐름

```text
Epic 생성 (기능 영역)
      ↓
Story 정의 (사용자 기능·완료 조건)
      ↓
파트별 Sub-task / 독립 Task·Bug 생성
      ↓
담당자 지정 및 Sprint 등록
      ↓
To Do → 작업 브랜치 생성·개발 시작 → In Progress
      ↓
개발 및 Commit (Jira 이슈 번호 포함)
      ↓
MR 생성 → In Review → 코드 리뷰·검증
      ↓
파트별 develop-* 병합 → 작업 이슈 Done
      ↓
각 파트 develop-* → 공통 develop 통합
      ↓
기능 연동 및 Story 검증 → Story Done
      ↓
전체 통합 테스트 및 안정화
      ↓
develop → master
```

**예시: 실종 신고 목록 조회**

```text
Epic: 실종 신고
└── Story: 일반회원이 실종 신고 목록을 조회한다
    ├── Sub-task: [Mobile] 실종 신고 목록 화면 구현
    ├── Sub-task: [Mobile] 실종 신고 목록 API 연동
    ├── Sub-task: [Backend] 실종 신고 목록 조회 API 구현
    └── Sub-task: [Backend] 목록 조회 테스트 작성
```

> 각 작업 이슈 번호는 실제 Jira에서 발급받아 작성한다. Story 기능에 참여하지 않는 파트의 작업을 형식적으로 추가할 필요는 없다.

| Commit 마지막 줄 | `S15P31D106-번호` 필수 |
| 작업 브랜치 | `타입/S15P31D106-번호-작업내용` |
| Jira Story | `[주체]가 [행동]한다` |
| 작업 이슈 제목 | `[파트] 구체적인 작업 내용` |
| 기본 상태 | To Do → In Progress → In Review → Done |
| 작업 브랜치 병합 | 해당 파트 `develop-*`, Squash Merge 권장 |
| 파트별 통합 | `develop-*` → `develop`, 이력 유지 |
| 최종 배포 | `develop` → `master`, 이력 유지 |
| 보호 브랜치 | 직접 Push 금지, MR 및 최소 1명 리뷰 |
| 작업 이슈 Done | 완료 조건 충족 및 필요한 리뷰·병합 완료 |
| Story Done | 관련 작업 완료 및 기능 연동·검증 완료 |

**핵심 원칙:** Jira에서 작업을 정의하고, 작업 브랜치에서 개발한 뒤, 리뷰와 검증을 거쳐 파트별·전체 통합 브랜치에 순차적으로 반영한다.
