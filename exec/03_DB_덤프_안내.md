# DB 덤프 안내

이 폴더의 `db/`에 제출용 DB 덤프 최신본을 둔다. 파일명 규칙: `db_dump_YYYYMMDD.sql.gz`

## 구성

DB는 k3s 클러스터 안의 PostgreSQL 17 단일 인스턴스다(StatefulSet `postgres`, 네임스페이스 `data`, 이미지 `pgvector/pgvector:pg17`). 매니페스트는 `infra` 브랜치의 `infra/platform/postgres/`에 있다.

DB 1개(`animal`) 안에 스키마 5개와 계정 6개로 소유권을 나눈다.

| 스키마 | 소유 계정 | 사용 서비스 | 테이블 생성 |
|---|---|---|---|
| `core` | `core_app` | core-api (chat·notification도 이 스키마의 테이블을 쓴다) | core-api의 Flyway |
| `chat` | `chat_app` | chat | |
| `notification` | `notification_app` | notification | |
| `simulation` | `simulation_app` | simulation | simulation의 Flyway |
| `ai` | `ai_app` | match-worker | match-worker가 기동 때 생성(`ai.reid_embeddings`) |

- 여섯 번째 계정 `dev_readonly`는 팀원 조회용 읽기 전용 계정이다.
- 확장: `vector`(유사도 매칭), `pg_stat_statements`.
- 계정·스키마·권한·확장은 볼륨이 비어 있을 때 ConfigMap `postgres-init`의 `01-init.sh`가 한 번 만든다.
- 테이블 정의는 `docs/animal_service_db_spec_v24.md`에 있다.

## 덤프 생성

계정과 권한까지 함께 떠야 하므로 `pg_dumpall`을 쓴다. 노드 1에서 실행한다.

```bash
sudo k3s kubectl -n data exec postgres-0 -- pg_dumpall -U postgres --no-role-passwords | gzip > db_dump_$(date +%Y%m%d).sql.gz
```

- `--no-role-passwords`로 계정 비밀번호 해시를 덤프에서 뺀다. 복원한 뒤 계정 비밀번호를 다시 설정해야 한다(복원 절 참고).
- 제출본 `db/db_dump_20261118.sql.gz`(2026-11-18 생성): 계정 7개(`postgres` 포함), 스키마 5개, 확장 2개, 테이블 47개(`core` 36, `simulation` 10, `ai` 1), 압축 전 약 1.4MB.
- 정기 백업은 CronJob `postgres-backup`이 6시간마다 S3(`s3://s15p31d106-backup-887324111755/postgres/`)에 올린다. 형식은 `pg_dump -Fc`(`animal-<시각>.dump`)와 `pg_dumpall --globals-only`(`globals-<시각>.sql`)이고 30일 보관한다.

## 검증

```bash
# 헤더 확인 ("PostgreSQL database cluster dump" 문구)
zcat db_dump_*.sql.gz | head -5

# 계정·스키마·확장 확인
zcat db_dump_*.sql.gz | grep -E "^CREATE (ROLE|SCHEMA|EXTENSION)"

# 테이블 수 확인
zcat db_dump_*.sql.gz | grep -c "^CREATE TABLE"
```

## 복원 (신규 환경)

PostgreSQL이 빈 볼륨으로 뜨면 초기화 스크립트가 계정·스키마·확장을 먼저 만든다. 그 뒤 덤프를 넣는다. 복원하는 동안 서비스가 DB에 쓰지 않도록 서비스 파드를 먼저 내린다(`infra` 브랜치에서 replicas를 0으로 커밋).

```bash
zcat db_dump_YYYYMMDD.sql.gz | sudo k3s kubectl -n data exec -i postgres-0 -- psql -U postgres -d postgres
```

- 초기화 스크립트가 이미 만든 계정·DB·스키마·확장에 대한 `already exists` 오류는 정상이다. 그 외 오류는 없어야 한다.
- 덤프에 Flyway 이력 테이블(`flyway_schema_history`)이 들어 있어, 서비스를 다시 띄워도 마이그레이션이 다시 실행되지 않는다.
- 덤프에 계정 비밀번호가 없다. 초기화 스크립트가 만든 계정은 SealedSecret `postgres-credentials`의 비밀번호를 그대로 유지한다. 초기화 스크립트 없이 복원했다면 `ALTER ROLE <계정> PASSWORD '...'`로 계정마다 비밀번호를 설정한다.
- `vector` 확장이 필요하므로 일반 `postgres` 이미지가 아니라 `pgvector/pgvector:pg17`을 쓴다.

S3 백업본(`.dump`)으로 복원하는 절차는 `infra/docs/rebuild-runbook.md` 1절에 있다.

## 덤프 없이 시작하기

덤프 없이도 서비스는 뜬다. 빈 DB에서 core-api와 simulation을 `dev` 프로파일로 띄우면 Flyway가 테이블과 기준 데이터(행정구역, 동물 품종, 입양 신청서 문항, 시뮬레이션 상점·이벤트)를 만들고, `db/dev`의 시연용 데이터도 넣는다. 이 경우 실제 사용자가 올린 게시글과 사진 정보는 없다.

## 로컬에서 확인

```bash
cd backend && docker compose up -d
zcat ../exec/db/db_dump_YYYYMMDD.sql.gz | docker compose exec -T postgres psql -U <DB_USERNAME> -d postgres
```

로컬 compose의 PostgreSQL은 `postgres:17-alpine`이라 `vector` 확장이 없다. `ai` 스키마 관련 구문에서 오류가 나며, 나머지 스키마는 복원된다.
